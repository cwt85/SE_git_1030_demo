# 資料庫分支交接說明

本分支實作基本版及 Pro 版，沿用《活動報名系統規劃.md》的表名、欄位與 API 路徑。依黑板架構，由 `main.py` 掛載 `route/`，路由呼叫根目錄 `DB.py`，畫面放在 `templates/`。

## 檔案與分工

| 檔案 | 用途 |
|---|---|
| `DB.py` | SQLAlchemy 模型、連線、活動與報名操作、錯誤類別 |
| `sql/001_initial.sql` | Adminer 可直接執行的初始建表 SQL，也是初始 Alembic migration 的來源 |
| `sql/002_demo_data.sql` | 可選的假資料，含開放、手動關閉、過期活動；僅執行一次 |
| `alembic/`、`alembic.ini` | 資料庫版本追蹤與未來遷移 |
| `.env.example` | 不含密碼的連線設定範例 |
| `requirements-db.txt` | 資料庫部分的必要套件 |
| `requirements-db-dev.txt`、`tests/` | 測試套件與 PostgreSQL 整合測試 |

整合時將 master 的 `index.html` 移至 `templates/index.html`，保留原有視覺與 Pro 提示並接上 PostgreSQL。完整網站套件與啟動方式見根目錄 README；`requirements-db.txt` 僅適用於資料庫部分。

## 本機啟動

使用 Python 3.10 以上版本。在專案根目錄執行：

```powershell
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements-db-dev.txt
Copy-Item .env.example .env
```

如果 `.env` 已存在，保留原檔，不要執行最後一行覆蓋它。
編輯 `.env`，設定 `DB_HOST`、`DB_PORT`、`DB_NAME`、`DB_USER`、`DB_PASSWORD`。
密碼含 `#` 或空白時請用適當引號包住；不要將 `.env` 提交到 Git。
環境變數優先於 `.env`。密碼使用 SQLAlchemy `URL.create()` 組合，不必自行做 URL 編碼。

目前這台電腦的資料庫為 `localhost:5432/event_registration`，帳號為 `postgres`；Adminer 網頁的 `9000` 不是 PostgreSQL 連接埠。
每位組員的 `localhost` 是各自的電腦。Git 分支傳遞程式與建表檔，不會傳遞實際資料庫或密碼；組員需要在自己的環境建立資料庫，或由團隊另外決定共用資料庫的位置。

## 建立資料表：二選一

先在 Adminer 建立 `event_registration` 資料庫，再選其中一種方式：

### 新環境：Alembic（建議）

```powershell
.venv\Scripts\python.exe -m alembic upgrade head
```

### 已經由 Adminer 建表的環境

在選取 `event_registration` 後執行 `sql/001_initial.sql`。
確認資料表結構與這個初始版本相同，再執行：

```powershell
.venv\Scripts\python.exe -m alembic stamp 0001_initial
.venv\Scripts\python.exe -m alembic check
```

`stamp` 只記錄版本，不能替代建表或修正不同的結構。這台電腦已透過 Adminer 建表，不應重跑初始建表 SQL。
`alembic_version` 是版本追蹤用的管理表；業務資料表仍只有兩張。
後續修改用新的 Alembic revision，勿修改已部署的 `001_initial.sql`。初始版本的 downgrade 預設拒絕執行，以免誤刪活動與報名資料。

## 資料表

### events：一筆代表一個活動

| 欄位 | 型別 | 規則 |
|---|---|---|
| id | BIGINT identity | 主鍵、自動編號 |
| title | VARCHAR(200) | 必填、不可全空白 |
| description | TEXT | 可空 |
| location | VARCHAR(255) | 可空 |
| starts_at / ends_at | TIMESTAMPTZ | 可空；都有值時結束不可早於開始 |
| registration_deadline | TIMESTAMPTZ | 可空；空值表示無時間截止限制 |
| status | VARCHAR(20) | open / closed / cancelled，預設 open |
| created_at / updated_at | TIMESTAMPTZ | 預設建立時間；DB.py 更新活動時維護 updated_at |

如果直接以 Adminer 或 SQL 修改活動，需同時更新 `updated_at`，例如 `updated_at = CURRENT_TIMESTAMP`。

### registrations：一筆代表一次報名

| 欄位 | 型別 | 規則 |
|---|---|---|
| id | BIGINT identity | 主鍵、自動編號 |
| event_id | BIGINT | 必填、外鍵指向 events.id |
| name | VARCHAR(100) | 必填、不可全空白 |
| phone | VARCHAR(30) | 必填、保留前置零 |
| created_at | TIMESTAMPTZ | 預設建立時間 |

- `(event_id, name, phone)` 不可重複。相同人可以報名不同活動；同名不同電話、同電話不同姓名也允許。
- 有報名紀錄的活動不能直接刪除，請改 `status`；此版不提供刪除、取消個人報名、會員、名額限制。
- `(event_id, created_at)` 索引支援活動報名清單。
- 報名人數由報名紀錄計算，欄位回傳名稱固定為 `registration_count`。
- `DB.py` 先去除姓名前後空白；電話做 NFKC 正規化，去除空白、括號、連字號。台灣手機 `+8869xxxxxxxx`、`8869xxxxxxxx` 統一為 `09xxxxxxxx`，與 master 的 Pro 功能一致；其他國碼保留。
- 直接寫 SQL 時，也應先統一格式；唯一限制只比較實際儲存值。

## Route 組員如何呼叫

```python
from DB import get_database, DatabaseError

db = get_database()
events = db.list_events(only_open=True)
event = db.create_event(title="校園活動", location="活動中心")
result = db.register(event["id"], name="測試同學", phone="0000000001")
db.update_event(event["id"], status="closed")
```

| 預定 API | 呼叫方式 |
|---|---|
| GET /api/v1/events | `db.list_events()`；僅列可報名活動用 `only_open=True` |
| GET /api/v1/events/{id} | `db.get_event(id)` |
| POST /api/v1/events/{id}/registrations | `db.register(id, name=..., phone=...)` |
| GET /api/v1/events/{id}/registrations | `db.list_registrations(id)`；公開結果只有姓名 |
| POST /api/v1/admin/events | `db.create_event(**payload.model_dump())` |
| PATCH /api/v1/admin/events/{id} | `db.update_event(id, **payload.model_dump(exclude_unset=True))` |
| GET /api/v1/admin/events/{id}/registrations | `db.list_registrations(id, public=False)`；含電話 |

查詢清單回傳 Python list；活動含 `registration_count`。報名成功回傳 `id`、`event_id`、`name`、`created_at`，不含電話。
活動/報名日期回傳有時區的 Python datetime，FastAPI 可序列化為 ISO 8601。
建立/更新活動傳入的時間需是有時區的 datetime，由 route 的 Pydantic 模型解析 JSON；不要把原始日期字串直接交給 DB.py。
`status="open"` 只篩選儲存狀態；`only_open=True` 才同時檢查截止時間。截止時無需排程把 status 改成 closed。

FastAPI 錯誤對應範例：

```python
from fastapi import HTTPException

try:
    return db.register(event_id, name=payload.name, phone=payload.phone)
except DatabaseError as error:
    raise HTTPException(status_code=error.status_code, detail=str(error)) from error
```

| 例外 | HTTP 狀態碼 |
|---|---|
| EventNotFound | 404 |
| DuplicateRegistration | 409 |
| RegistrationClosed | 400 |
| InvalidInput | 422 |

未知資料庫連線錯誤由後端統一記錄並回傳一般錯誤訊息，不把原始 SQL 或連線資訊回傳瀏覽器。
這是同步 SQLAlchemy，建議 route 使用一般 `def`；若用 `async def`，須放入 threadpool，避免阻塞事件迴圈。
`get_database()` 可重複使用，但每個方法都會建立自己的 Session/transaction，不共用 Session。

## 報名與關閉的交易規則

`register()` 與 `update_event()` 都先鎖住該筆活動，避免手動關閉與報名交錯造成錯誤。
取得鎖後，報名使用 PostgreSQL `clock_timestamp()` 檢查當下時間；等於截止時間也拒絕。
成功後才提交交易，失敗會回滾。唯一限制衝突會轉成 DuplicateRegistration，後續操作仍可正常執行。
此規則在 DB.py 資料操作層落實；直接從 Adminer 新增報名不會執行 Python 的截止檢查。

## 前端整合注意

整合後的 `templates/index.html` 使用實際 API，已移除 localStorage 報名備援。只有 API 成功才顯示成功；斷線顯示錯誤，初始載入失敗時可按重新載入。
公開頁 `/` 的名單只顯示姓名；管理頁 `/admin` 讀取完整名單並提供新增活動與停止報名。
本分支沒有實作管理員身分驗證；沿用計畫書的本機課程展示範圍。

## 驗證

```powershell
.venv\Scripts\python.exe -m pytest -q
```

測試在本機 PostgreSQL 建立交易內的獨立 schema，結束時整個回滾，不修改 public 的活動及報名資料。
涵蓋電話格式、缺漏與錯誤輸入、正常報名、人數、公開/管理名單、重複及跨活動報名、手動關閉、取消、截止、外鍵、不可刪有報名的活動、時間順序，以及 SQL 字串作為一般資料儲存。
每次整合測試也執行初始 Alembic migration。

實作參考：[SQLAlchemy Session](https://docs.sqlalchemy.org/en/20/orm/session_basics.html)、[PostgreSQL Constraints](https://www.postgresql.org/docs/17/ddl-constraints.html)。
